# 12. 仅注册模式与跨端通知设计（草案）

> 状态：Draft v0.2 · 2026-11-09
> 范围：设计讨论，未实现。`codex queue` 与 Claude Channel 的门控已在 dev 实测（见第 8 节）；Claude 侧 `asyncRewake` / inbox socket 旁路未验证。

## 1. 问题

AgentBridge 现在要获得“把消息写回活动会话”的能力，必须由 ABG 启动 Agent：

- `abg codex` 启动 Codex TUI，并接管它的 app-server 连接；
- `abg claude` 以 `--channels` 启用 Claude Code 的 Channel 插件。

这件事解决了回写，但把接入方式绑死在“包装启动”上。目标是支持**只登记已经在运行的会话**，不要求用户改用 `abg` 启动 Agent。

## 2. 现状（已核对）

### Codex

- 注入走 app-server `turn/start`，参数是 `input: [{ type: "text", text }]`，协议层面就是一条**用户输入**；忙时可用 `turn/steer` 插入当前回合。
  实现：`src/codex-adapter.ts:519`（`injectMessage`）、`:558`（`steerMessage`）。
- 前提是连到该 thread 实际所在的 app-server 实例；只知道 thread ID 不够。
- CLI 0.167.0 自带 `codex queue --thread <UUID|name> --message <TEXT> [--resume] [--remote ws://...]`，提供原生的“排队 + 唤醒”入口。它不是向运行中回合实时插入的通道。

### Claude Code

- 推送走 `notifications/claude/channel`，`meta.user` 标 `Codex` 或 `Room`，只是来源标签，不代表真人身份。
  实现：`src/claude-adapter.ts:269`（`pushViaChannel`）。
- 前提是会话启动时已启用对应 Channel。普通已运行会话不能靠事后登记获得推送能力。

### 房间与跨机器

- 链路：发送端 daemon → broker 广播 → 对端 daemon → Channel 推送。
  实现：`src/broker.ts:122`、`src/room-bridge.ts:217`。
- 离线使用 `store_if_offline` 暂存，接收端按 message id 去重。
- 已知限制：每目标暂存上限约 1000、无应用层 ack、成员撤销后不补发。

## 3. 关键结论

1. **登记会话身份 ≠ 获得接收能力。** 注册只解决“发给谁”，不解决“怎么送进去”。
2. **消息走用户输入接口 ≠ 经过真人授权。** 自动接收、人工确认必须单独建模，不能把“能注入”当成“已授权”。
3. **推送成功 = 已提交，不等于已读或已执行。**
4. 不同 Agent 的能力不同，必须按 Agent + 宿主 + 版本登记，不能用统一承诺覆盖。

## 4. 能力矩阵

| Agent / 形态 | 接收方式 | 前提 | 忙时行为 | 成熟度 |
|---|---|---|---|---|
| Codex（ABG 包装） | `turn/start` / `turn/steer` | ABG 持有 app-server | 可靠 steer | 已上线 |
| Codex（仅注册，本机） | `codex queue --thread <UUID>` + 健康探测 | 同机同 `CODEX_HOME`，queue 能解析 thread | 排队并入下一回合，不打断当前回合（实测约 26s 后由 `trigger=queue` 拉起） | 已实测可行 |
| Codex（仅注册，远端） | `codex queue --remote` | 可访问远端 app-server + 鉴权 | 未知 | 未验证 |
| Claude（Channel） | `notifications/claude/channel` | 会话启动时 `--channels` 启用 | 宿主排队/展示 | 已上线 |
| Claude（仅注册） | 无原生推送 | 未启用 Channel 时 Channel 不运行 | — | 只能拉取 |
| 任意 Agent | 收件箱 + `receive` 工具 | Agent 主动调用 | 空闲不会唤醒 | 通用兜底 |

实测结论见第 8 节。一句话：Codex 侧可以只登记不接管（`codex queue` 排入下一回合），Claude 侧不行——Channel 必须在会话启动时开启。

## 5. 设计

把“身份”“通道”“策略”拆成三层：

### 5.1 SessionRegistry

登记项至少包含：

```text
sessionId, agent, host, cwd, threadId, endpoint,
capabilities[], capabilityEvidence, lastSeenAt
```

`capabilities` 是能力声明，不是承诺；`capabilityEvidence` 记录该能力最近一次实测的时间与结果。

### 5.2 ReceiveAdapter

每种接收能力一个适配器：

- `codex-queue`：`codex queue`，可选 `--resume` / `--remote`
- `claude-channel`：仅限启动时启用 Channel 的会话
- `inbox-pull`：写入持久收件箱，由 Agent 主动拉取

适配器负责“能不能送”，不负责“该不该送”。

### 5.3 DeliveryPolicy

- `auto`：仅当接收能力可靠且忙闲可观测时开放
- `confirm`：需要人工确认后投递
- `idle-only`：只在对端空闲时投递
- 投递失败统一回退到收件箱，不假装成功

### 5.4 投递流程

```text
send
  → resolve session
  → select adapter by capability
  → deliver
       ↘ fail / no capability → inbox (store_if_offline)
```

登记命令只写 registry，不承诺推送能力；`abg doctor` / `abg pairs` 展示能力与验证状态。

## 6. 分阶段落地

| 阶段 | 内容 | 依赖 |
|---|---|---|
| P0 | 收件箱 + 手动拉取，跨 Agent 通用 | 无 |
| P1 | Codex `codex queue --resume`（本机） | 忙时/空闲语义验证 |
| P2 | Claude 仅限启动时启用 Channel 的会话，能力显式标记 | 插件能力探测 |
| P3 | 远端 app-server（鉴权、租户隔离、重放） | 远端端点与凭据管理 |

## 7. 非目标

- 用终端按键注入（`tmux send-keys`）作为统一接收方案；它依赖终端环境，容易与人工输入、审批界面冲突。
- 对任意已运行会话承诺推送。
- 把“消息进入用户输入通道”当成“已获得真人授权”。

## 8. 实测结论（dev，2026-11-09）

由 dev 上的 `abg-notify` pair 执行，全程未改 ABG 代码、未占用生产 pair 的端口。

### 8.1 Codex `queue`

- **回合进行中投递**：消息进入队列，当前回合不被打断；约 26s 后由 `trigger=queue` 起新回合消费。
- **卡住场景**：`turn_aborted` 之后队列可能滞留；在还能拿到该会话 app-server RPC 的前提下，`thread/queue/start` 可把滞留消息拉起。
- **并发写入**：同一 thread 的第二个 app-server 被拒绝（`already has an active writer`，code `-32600`）。即一个 thread 同时只有一个 writer，ABG 不能假设可以和外层 TUI 并行挂一个 app-server。
- **双 TUI 打开同一线程**：只产生一个回合，未见重复消费。
- **失败表现**：线程不存在 `no rollout found`（`-32603`）；`--thread <name>` 遇到重名 `Multiple sessions match`；端点不可达 `Connection refused (os error 111)`。
- **语义提醒**：`queue` 走的是用户输入通道，ABG 自己的 `meta`（来源标签）会丢失，需在正文自带来源前缀（如 `[ABG:Codex|Room]`）；`clientUserMessageId` 的队列级去重语义未验证，ABG 仍需按自己的 message id 去重。

### 8.2 Claude Channel 门控

- 会话未带 `--channels` 时 Channel 不会运行：Claude 2.1.319 二进制中存在 `... not in --channels list for this session`，官方文档亦为 "no channel runs until a user opts it in for the session with `--channels`"。
- 因此“仅注册”在 Claude 侧只能回退到收件箱拉取；`asyncRewake` 与 inbox socket 属于未验证旁路，是否做 PoC 待定。

### 8.3 推荐的投递策略（Codex 仅注册）

1. 优先 `codex queue --thread <UUID> --message <TEXT>`，不用 `--thread <name>`，避免重名歧义。
2. 投递后做健康探测：查 `thread/queue/list` 与 rollout 是否出现 `turn_trigger: "queue"`。
3. 若 N 秒未消费且能拿到该会话的 app-server，调 `thread/queue/start` 兜底；拿不到 RPC 时保留持久队列并显式告警，不假装成功。

## 9. 仍未验证

- `--resume` 是否改变 thread 标题或模型；缺 daemon 时是否只告警不消费。
- `--remote` 的鉴权方式与失败表现。
- Claude Channel 能否热加载；`asyncRewake` / inbox socket 是否可作为仅注册旁路。
- 跨机器 broker：每目标队列上限（约 1000）、无应用层 ack、成员撤销后不补发。
- `clientUserMessageId` 在队列层的去重语义。
